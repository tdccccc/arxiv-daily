# 筛选质量评估

回答一个问题：日报的论文筛选，选得准不准？

做法是：每天日报完成后，系统会把当天所有候选论文的筛选结果（包括被判为不相关的）留下来。你从中抽一批，对照标题和摘要写下“这篇该选 / 不该选 / 属于哪个方向”，再用脚本算出：

- 该选的论文，筛选选中了多少（召回率）；
- 筛选选中的论文，有多少真的该选（精确率）；
- 选对的论文里，方向判对了多少。

同一份标注可以反复使用：改了提示词或换了模型之后，用同一份标注重跑一遍，就能直接比较前后的差别。

这是开发者工具，不属于产品的命令，不会出现在 CLI 或 Obsidian 插件里，也不在 CI 里运行。CI 只跑这些脚本自带的测试，测试不访问网络、不调用模型。

## 开始之前

1. 在仓库根目录安装过依赖：`npm ci`。脚本运行时会现场编译，不需要另外构建。
2. 日报至少已经成功跑过几天。每次日报完成后，CLI 或 Obsidian 插件会在 Vault 里留下一份当天的筛选记录：

   ```
   <Vault>/arxiv-daily/.index/filter-decisions/YYYY-MM-DD.json
   ```

   如果你改过输出目录，它在你设置的索引目录下的 `filter-decisions/` 里。记录只保留最近 180 天，更早的会在写入新记录时自动清理。没有记录的日子无法评估。
3. 以下命令都在仓库根目录运行。

## 第 1 步：导出标注表

```sh
node scripts/quality-eval/export.mjs --out ~/quality-eval/sheet-1 --vault ~/arxiv-daily --from 2026-10-10 --to 2026-10-14
```

这一步不调用模型。参数：

| 参数 | 含义 |
| --- | --- |
| `--out <目录>` | 必填。文件放在这里。 |
| `--vault <目录>` | Vault 根目录。不写时用 CLI 配置文件里的 `vault_root`。 |
| `--config <文件>` | 指定 CLI 的 `config.toml`（决定 Vault 位置和输出目录结构）。不写时用 CLI 默认的那份。 |
| `--from <日期>`、`--to <日期>` | 只取这个日期范围内的日报，格式 `YYYY-MM-DD`，两端都包含。不写就取全部记录。 |
| `--skipped <数量>` | 在“全部被选中的论文”之外，再随机加入多少篇被判为不相关的论文，默认 50。 |
| `--seed <文字>` | 随机抽样的种子。同样的记录和种子，抽到的论文完全一样。 |
| `--force` | 允许覆盖已有的 `labels.csv`。 |

导出的论文由两部分组成：当天被选中的每一篇，加上随机抽出的一部分被判为不相关的。后者是为了查“该选却没选”的漏网之鱼；抽得越多，对漏选的估计越可靠，表格也越长。

`--out` 目录里会有：

| 文件 | 内容 |
| --- | --- |
| `labels.csv` | 标注表，用表格软件打开并填写。 |
| `labels.guide.md` | 填写说明和方向编号表（给标注的人看）。 |
| `labels.meta.json` | 抽样种子、日期、当时的模型和提示词版本、方向编号表。评估时要用，请和 `labels.csv` 放在一起。 |
| `abstract-cache/`、`abs-cache/` | 已取回的摘要缓存。 |

几点说明：

- 摘要不保存在筛选记录里，导出时从 arXiv 现取。查询接口一旦限流（HTTP 429），本次导出的接口请求不会重试：同一进程内该主机进入冷却，后续批次立即失败，所以本次导出剩余的论文全部改从 `arxiv.org/abs/<编号>` 页面读取摘要，每篇间隔约 3 秒，几十篇可能要等几分钟。脚本会停止调用接口并只给出一条汇总警告；实在取不到的论文摘要留空，并给出警告。
- 已取回的摘要有缓存（`abstract-cache/`、`abs-cache/`），重跑时直接复用，不会重复请求；稍等一段时间后重新运行（新进程不受上次冷却影响）就可以继续用查询接口。
- 如果 `labels.csv` 已存在，脚本会拒绝覆盖，免得冲掉你已经填好的标注。确定要重新生成才加 `--force`；已经开始标注后请换一个 `--out`。

## 第 2 步：标注

用 Excel、WPS 或 Numbers 打开 `labels.csv`，保存时请继续选 CSV（UTF-8）格式。先读一遍 `labels.guide.md`，里面有方向编号表。

只需要填三列，其余列不要改：

| 列 | 怎么填 |
| --- | --- |
| `label` | `y`：这篇论文应该被选中（确实属于你关注的某个方向）；`n`：不应该。不区分大小写。 |
| `label_direction` | 只有 `label` 是 `y` 时才填：它属于方向编号表里的哪个编号。属于多个方向就用英文分号隔开，如 `1;2`。 |
| `note` | 随便备注，不影响计算。 |

建议和注意：

- **先把 `model_category`、`model_directions`、`model_score`、`model_outcome` 这几列隐藏起来**（表格软件里选中列后“隐藏”），不要看模型当时怎么判断的，否则容易被它带偏。
- 标准是“这篇论文该不该出现在日报里”，不是“我会不会去读”。
- 拿不准的行留空，评估时当作未标注，不计入任何指标。
- `abstract` 为空表示这次没取到摘要，可以按标题判断，或打开 `https://arxiv.org/abs/<编号>` 看。
- `had_abstract_at_filter` 为 `false` 说明筛选当时模型只看到了标题。这些行照常标注。
- 填错了也不会悄悄算错：评估时会列出出问题的行号（比如 `label` 写成了别的字，或者方向编号不在表里），改好再运行即可。
- 一次标注 30 篇以上，数字才有参考价值；被选中的论文如果只有几篇，指标会跳动很大。

## 第 3 步：评估

### 3a. 只给记录下来的判定打分（免费，不调用模型）

```sh
node scripts/quality-eval/evaluate.mjs --sheet ~/quality-eval/sheet-1/labels.csv --out ~/quality-eval/sheet-1/report-recorded --recorded
```

评估的是日报当时的筛选结果。`--meta <文件>` 可以指定元数据文件，不写则使用 `labels.csv` 旁边的 `labels.meta.json`。

### 3b. 用当前的提示词和模型重新筛一遍

```sh
# 先看计划，不会调用模型
node scripts/quality-eval/evaluate.mjs --sheet ~/quality-eval/sheet-1/labels.csv --out ~/quality-eval/sheet-1/report-run-1 --runs 3

# 确认后加上 --yes 才会真正调用
node scripts/quality-eval/evaluate.mjs --sheet ~/quality-eval/sheet-1/labels.csv --out ~/quality-eval/sheet-1/report-run-1 --runs 3 --yes
```

这一步会调用你 CLI 配置里的模型，**要花钱**。不加 `--yes` 时只会打印这样一行计划然后退出（退出码 0，不调用、不写文件）：

```
This will make 3 model calls (one request per run), each with 12 papers (about 19618 characters of prompt), using <模型> via <服务商>. Topics come from the sheet's direction snapshot.
```

- 每次运行只发一个请求，里面是所有已标注（`y` / `n`）的论文，带着表里的摘要；未标注的行不发送。请求和结果检查都复用日报流水线的代码。筛选当时只看到标题的论文，重跑时也会带上导出阶段补取的摘要；报告开头会提示有多少篇属于这种情况，对比表另有一节“只看筛选时有摘要的行”，在输入一致的论文上比较。
- `--runs N`（1 到 20，默认 1）：重复运行 N 次。模型即使设置了温度 0，同一批论文两次结果也可能不同，所以比较前后差别时建议至少跑 3 次。
- `--config <文件>`：指定模型设置所在的 CLI `config.toml`，不写则用 CLI 默认的那份。API 密钥和接口地址不会写进报告或输出。
- 方向列表默认用标注表记录的那份（也就是标注时模型看到的方向），这样每次重跑的条件一样。如果想测试“方向措辞改了以后筛选会怎样”，加 `--topics-from-config`，改用配置文件里的主题；此时如果方向文字和标注时不同，报告开头会有醒目的提示，方向准确率和分主题结果会被隐藏（选中与否的指标仍然照常给出）。
- 限制：如果标注表跨了几天，而这几天用的方向列表不一样，默认方式无法重跑，会报错。请一天一天分别导出，或者加 `--topics-from-config`。同一篇论文在表里出现两次也会报错。
- 某一次运行失败（接口出错或回答格式不对），只影响那一次：报告里会写明原因，其余运行继续。全部失败时命令以非零状态退出，报告仍会写出。
- 脚本会先检查并创建 `--out` 目录，再调用模型；目录建不出来或不可写时立即报错，不会先花钱再失败。不加 `--yes` 的试运行不写任何文件，但如果目标位置明显不可用（例如 `--out` 位于一个普通文件之下）也会提前报错。
- `--out` 里已有 `report.md` 或 `report.json` 时默认不会被覆盖，脚本会在调用模型之前报错；确定要替换时加 `--force`。

输出目录里有 `report.md`（给人看）和 `report.json`（给程序读）。

## 怎么看报告

报告都是中文。几个核心指标，每个一句话：

- **精确率（样本内）**：筛选选中的论文里，有多少是你标了 `y` 的。低说明选得太杂，噪声多。样本内按表里的行直接计数。记录的判定里选中的论文都来自“被选中”层，这个数没有偏差；重跑如果选中了抽样的“被判不相关”行，样本内精确率会偏高，应看加权估计。
- **召回率（样本内）**：你标了 `y` 的论文里，筛选选中了多少。低说明漏掉了该选的。漏选多在被判不相关的抽样行里，所以样本内召回率同样偏高，重跑时以加权估计为准。
- **F1（样本内）**：精确率和召回率的综合，两者都高才高。一篇都没选中、或表里没有应选的论文时，F1 为 0；只有完全没有可评分的论文（真正例、假正例、假反例都是 0）时才显示 `n/a`。
- **加权估计（精确率 / 召回率 / F1）**：表里只抽了一部分“被判为不相关”的论文，直接算的精确率和召回率会偏离真实情况。加权估计把这部分抽样还原到全部被判不相关的论文上，更接近真实的漏选和误选情况。只有在元数据里有被判不相关的总数时才给出；排除“无摘要”行的那一行不加权。记录的判定里加权精确率与样本内精确率相同（选中的论文都来自被选中层，权重为 1）。
- **方向判对了多少**：在选中且你也标 `y` 的论文里，你标的方向只要有一个在模型给的方向里，就算判对；没填方向的不计入。
- **不同分数线下的结果**：模型给每篇论文打 0–100 的相关度分。表里列出分数线分别取 0、50、60、70、80、90 时的精确率和召回率，并另给加权估计，帮你判断把门槛定在哪里合适。
- **分主题**：每个主题单独的精确率和召回率，表头区分样本内和加权估计；加权召回把该主题的漏选按抽样比例还原，加权精确率只在重跑时可能与样本内不同。每个主题落到抽样层里的行可能很少，括号里的行数可以帮助判断估计的波动。
- **分歧列表**：漏选、误选、方向不一致的论文，附标题、分数和你的备注，是改进提示词时最有用的部分。“筛选时有摘要”列取标注表里的原值，表示日报筛选时有没有摘要（重跑请求里是否带摘要是另一回事）。
- **只看到标题的论文**：筛选时没有摘要的论文，判断依据弱得多。报告里“全部已标注行”之外，另有一行排除了这些论文的结果，两行对比看就知道摘要缺失造成了多大影响。
- **运行之间是否稳定**（只在重跑多次时出现）：多次成功运行里，有多大比例的论文每次选中与否都一样，以及哪些论文摇摆不定。摇摆多说明这个模型在这套提示词下不稳定，单次结果要谨慎看待。
- **记录的判定与重跑对比**（重跑时出现）：同一批论文，日报当时的结果和每次重跑的结果并排放在一起。比较改动前后请看加权列；“只看筛选时有摘要的行”一节只在两边都有摘要的论文上比较，输入一致，更容易解释。

每个比例后面括号里的数字是行数（如 `66.7%（4/6）`）。分母为 0 的指标显示 `n/a`，表示这批数据里没法算，不是 0；F1 只有在真正例、假正例、假反例全为 0 时才显示 `n/a`。加权估计按抽样比例折算，权重可能不是整数，所以不附行数。

## 比较一次提示词或模型的改动

1. 导出并标注一份固定的标注表（尽量不少于 30 篇，且包含一些该选的论文）。之后的比较都用同一份，不要重新导出。
2. 改动之前先建立基线：在当前的提示词和模型下重跑，`--runs 3 --yes`，输出到一个带日期的目录，例如 `report-before-2026-10-20`。如果想知道日报当时的表现，再加一次 `--recorded`。
3. 修改提示词（`packages/core/src/prompts/paper-filter.system.md`）或在 CLI 配置里换模型，然后用同一份标注表、同样的 `--runs` 再跑一次，输出到另一个目录。
4. 对比两份 `report.md` 的“记录的判定与重跑对比”表和分歧列表。报告头部写明了提示词版本、模型和日期，可以确认比的确实是改动前后。看加权精确率、加权召回率和加权 F1 的变化是否超出“运行之间摇摆”的范围，再决定改动是否有效；样本内精确率在重跑选中抽样行时会偏高，不要用它比较。如果表里有筛选时只看到标题的论文，再看“只看筛选时有摘要的行”一节做输入一致的对照。
5. 改的是方向措辞（不是提示词）时，用 `--topics-from-config` 重跑，只比较选中与否的指标。

# 摘要质量离线检查

回答另一个问题：已经写进 Vault 的日报条目和详细笔记，格式有没有问题？

它只做不需要模型的检查：回退比例、公式写法、字段长度、“原文未说明”、提示词禁止的空话、详细笔记的章节是否齐全。不判断内容对不对，也不联网、不调用模型，所以免费，可以随时重跑。

```sh
node scripts/quality-eval/summary-check.mjs --vault ~/Notes --out ~/quality-eval/summary-2026-10-28
```

在仓库根目录运行。参数：

| 参数 | 含义 |
| --- | --- |
| `--out <目录>` | 必填。`report.md` 和 `findings.json` 放在这里。 |
| `--vault <目录>` | Vault 根目录。不写时用 CLI 配置文件里的 `vault_root`。 |
| `--config <文件>` | 指定 CLI 的 `config.toml`（决定 Vault 位置和日报、笔记目录）。 |
| `--daily-dir <目录>`、`--papers-dir <目录>` | 日报和详细笔记所在目录，相对于 Vault。不写时用配置里的，再不然用 `arxiv-daily/daily` 和 `arxiv-daily/papers`。 |
| `--from <日期>`、`--to <日期>` | 只看这个日期范围内的日报，格式 `YYYY-MM-DD`，两端都包含。笔记按它链接的日报日期或 `published` 日期归入范围，没有日期的笔记始终包含。 |
| `--sources <目录>` | 可选。`summary-sources.mjs` 缓存的原文目录。加上它，报告会多一项“数字能否在原文中找到”：把日报字段和笔记正文里的数字到原文里查找，找不到的列为“疑似无出处数字”，需要人工核对。没有原文缓存的条目不参与这一项；不加则不做这项检查。 |
| `--force` | 允许覆盖 `--out` 里已有的 `report.md` 和 `findings.json`。不写时遇到已有报告会直接报错，免得冲掉要留存的报告。 |

只评估当前格式：五字段日报（2026-06-12 起）和带“研究问题”章节的详细笔记。更早的旧格式日报和笔记只计数，不评估。

`--out` 目录里会有：

| 文件 | 内容 |
| --- | --- |
| `report.md` | 给人看的中文报告：评估范围、各项比例、字段长度（含按月的核心结果长度）、详细笔记的章节分组、问题清单。 |
| `findings.json` | 给程序读的完整结果：每条日报条目、每篇笔记的全部发现，以及汇总数字。报告里的问题清单每类只列前 30 条，完整的在这里。 |

怎么看报告：

- **提示词哈希**：报告写出评估时仓库里两份提示词文件的 SHA-256 前 12 位。日报和笔记本身不记录生成时用的模型和提示词版本，所以哈希只说明“评估时的提示词”，不能证明内容就是用它们生成的。想比较改提示词前后的变化，请把改动前后的报告各留一份，用哈希确认比的是哪一版。
- **核心结果长度**：提示词要求“通常 80–180 个汉字”，这只是参考范围。报告按月份给出中位数、第 90 百分位和落在范围内的比例，可以看出提示词改动有没有改变长度。长度按去掉 `$...$` 公式和空白后的字符数计，标点、字母、数字都算在内。
- **核心规则误报**：核心代码的公式规则把 `$` 后紧跟数字当作货币符号，所以 `$6:1$`、`$8:1:1$` 这样的比值（连同同一行里连带的“未闭合”“嵌套”）和 `(0, 0.15]`、`[0,1)` 这样的半开区间（报“括号不成对”）会被误报，它们在 Obsidian 里渲染正常。报告把这些单独列在“core 规则误报（渲染正常）”下，不计入缺陷数字。
- **旧版本笔记**：详细笔记含提示词现在要求的全部章节才算“当前版本”，只有它们会被检查章节多余或顺序不对；缺章节的是更早的提示词写的，只按章节顺序分组汇总，不算违规。
- **疑似无出处数字**：数字没在原文里找到，不等于模型编造。可能是原文只在表格或图里给出、数值是模型由原文数字算出来的、单位换算过（Mpc 与 kpc）、规范化没覆盖的写法（如 `0.^{\prime\prime}18` 这种角秒写法），或原文版本和生成时不同。写成“约 450”这类以 0 结尾的整数按末位取整比较；其他整数必须逐字相同；带小数的数按摘要自己的精度取整后相同即算找到（摘要写 0.25，原文 0.248 算找到；摘要写 0.248，原文只有 0.25 不算）。只能当作人工核对的线索。
- **“原文未说明”、“作者声称”**：提示词要求信息缺失时这样写，所以它们是参考数字，不是缺陷。

## 缓存摘要所依据的原文

后面的检查（数字能否在原文里找到、模型评审）需要看到“当时模型读到的原文”。日报和笔记生成后不保存原文，所以要重新取一次：

```sh
# 先看计划，不联网
node scripts/quality-eval/summary-sources.mjs --vault ~/Notes --sources ~/quality-eval/sources

# 确认后加 --yes 才会真正请求 arXiv
node scripts/quality-eval/summary-sources.mjs --vault ~/Notes --sources ~/quality-eval/sources --yes
```

这一步**会向 arXiv 发很多请求**（不调用模型）：每篇论文至少一个，没有渲染版网页时最多三个（网页、LaTeX 源码、abs 页），请求之间至少隔 3 秒，沿用日报流水线的限流和冷却。不加 `--yes` 只打印要取多少篇、已缓存多少篇和预计时间，不发请求、不写文件。参数：

| 参数 | 含义 |
| --- | --- |
| `--sources <目录>` | 必填。缓存放在这里。 |
| `--vault`、`--config`、`--daily-dir`、`--papers-dir`、`--from`、`--to` | 与 `summary-check.mjs` 相同，决定取哪些论文：日期范围内日报里的五字段条目，加上详细笔记。 |
| `--fallbacks` | 回退条目（日报里只有原始摘要的论文）默认不取，加上它才取。 |
| `--limit <数量>` | 这次最多取多少篇，试跑时用。 |
| `--refresh` | 已缓存的也重新取（同时清掉网页缓存，会真的再请求 arXiv）。 |
| `--yes` | 真正发请求。 |

取原文用的是日报流水线自己的取法和同样的章节、全文字数上限（默认每节 16000、全文 100000 字符；用 `--config` 时取配置里 `[advanced]` 的值），上限会写进每条记录。目录里有：

| 文件 | 内容 |
| --- | --- |
| `<arXiv 编号>.json` | 一篇论文一个文件：取回时间、用了哪条路径（`html` 渲染版网页 / `latex` 源码 / `abs` 只有摘要页）、arXiv 版本（尽力从网页里读，读不到是 `null`，LaTeX 源码一定是 `null`）、字数上限、`abstract`、`abstractConclusion`、`fullSections`、取不到全文时的原因，以及内容哈希。 |
| `failures.json` | 没取成功的论文和原因。下次运行会再试，取成功后自动从里面删掉。 |
| `.cache/` | 网页和源码的原始缓存，换了字数上限重跑时不用再请求 arXiv。 |

可以随时中断，用同样的命令继续：已有记录的论文会跳过（字数上限变了的记录除外，会重取）。arXiv 要求稍后重试（限流冷却）时脚本立即停止，打印还剩多少篇没取，之后再运行即可；连续失败 10 篇也会停下。只有 abs 摘要页的论文记录里 `fullSections` 是 `null`，与当时生成日报时的输入一致。

注意：这是**现在**的 arXiv 内容，论文可能已经更新过版本，与当时模型读到的不一定完全一样；记录里的 `arxivVersion` 和取回时间用来说明这一点。

# 摘要的大模型评审

回答第三个问题：摘要有没有说错、漏掉关键内容、让读者看不懂？离线检查（上一节）看不出这些，需要另一个大模型对照原文来判断。

评审模型必须和写摘要的模型不同。给评审一个单独的配置文件，只放 `[llm]` 一张表（和 `scripts/acceptance` 的 `--model-config` 同格式），建议 `chmod 600`：

```toml
[llm]
base_url = "https://…/v1"
api_key = "…"
model = "评审用的模型名"
provider = "openai"          # 可选；不写会用默认值，报告里记录的服务商就不准
reasoning_effort = "medium"  # 可选
thinking_mode = false        # 可选
```

脚本把评审模型名和生成模型名（`--config` 指定的 CLI 配置里的 `[llm].model`，没有 `--config` 时用 CLI 默认配置；都读不到就要用 `--generator-model <名字>` 明确给出）比较，不区分大小写和首尾空格，相同就拒绝运行。接口地址和密钥不会写进任何输出文件或屏幕。

评审用的原文要先缓存好（上上一节的 `summary-sources.mjs`）。三步：

```sh
# 1. 先看计划：抽到多少条、哪些没有原文被跳过、最多多少次请求、约多少输入 token。不调用模型，不写文件。
node scripts/quality-eval/summary-judge.mjs --judge-config ~/judge.toml --config ~/.config/arxiv-daily/config.toml \
  --sources ~/quality-eval/summary-sources --out ~/quality-eval/judge-1 --daily 40 --notes 10

# 2. 确认后加 --yes 才真正调用模型（会花钱）
node scripts/quality-eval/summary-judge.mjs … --yes

# 3. 之后只想重新生成报告（不调用模型）
node scripts/quality-eval/summary-judge.mjs --report-only --out ~/quality-eval/judge-1 [--offline ~/quality-eval/summary-…-offline/findings.json]
```

**费用提醒**：每条要把约 8 万字符的原文连同摘要发给评审模型，50 条大约一百五十万输入 token；评审回答不合格时会重试一次，所以最多是计划里请求数的上限。先用 `--daily 2 --notes 1` 试一两条再放大。

参数：

| 参数 | 含义 |
| --- | --- |
| `--judge-config`、`--sources`、`--out` | 必填（`--report-only` 时只要 `--out`）。 |
| `--daily N`、`--notes M` | 评审多少条日报条目、多少篇详细笔记，默认 20 和 5。日报条目按月份按条数比例分配，月内按种子随机；笔记默认只抽按当前提示词写的。 |
| `--seed`、`--ids a,b,…` | 固定种子可复现同一批；`--ids` 直接指定论文（它的日报条目和笔记都评），不再抽样。 |
| `--include-older-notes` | 也抽更早提示词写的笔记（它们照样按当前提示词评）。 |
| `--from`、`--to`、`--vault`、`--daily-dir`、`--papers-dir` | 与其他命令相同。 |
| `--rejudge` | 已评审过的也重新评。评审模型、评审提示词和原文都没变时，重跑会跳过已评审的条目，可以中断后继续。 |
| `--offline <findings.json>` | 带 `--sources` 跑出来的离线检查结果。报告多一节“与离线检查对照”，看评审和数字溯源是否指向同一处。 |

`--out` 里有：`judgments/`（每条一个文件，含评审的原始回答、校验失败的原因、重试情况）、`run.json`（参数、种子、抽到的编号）、`report.md`（中文报告）、`judgments.json`（报告用到的全部数据）。

怎么看报告：

- **判定分布**：准确、完整、清楚各有多少条 ok / minor（小问题）/ major（大问题）。
- **问题清单**：每个问题带摘要原句、原文依据和说明；“原文未提及”表示评审认为摘要的这个说法在原文里找不到依据。大问题排在前面，每类只列前 30 条，其余在 `judgments.json`。
- **评审质量**：评审回答中有多少条一次就符合格式、多少条重试后才合格、多少条无效；无效或出错的条目不进入判定分布。这反映的是评审模型遵守输出格式的程度，不是摘要的质量。
- 评审也会出错：引用已由程序核对过确实存在，但“这算不算问题”仍是评审模型的判断，需要人工抽查。

## 在缓存原文上重新生成摘要

历史上的日报条目和笔记，写的时候读到的原文可能和现在缓存的不一样（论文后来更新了版本、提取方式也变过），直接评审会把“输入变了”误当成“模型写错了”。所以基线评审的对象是**重新生成**的摘要：用缓存的原文，按现在的提示词和生成模型再写一遍，再让评审模型评这一版。这样输入完全一致，改提示词或换模型前后也能直接比。

```sh
# 先看计划：不调用模型，不写文件
node scripts/quality-eval/summary-regenerate.mjs --config ~/.config/arxiv-daily/config.toml --vault ~/Notes \
  --sources ~/quality-eval/summary-sources --out ~/quality-eval/regen-1 --daily 40 --notes 10 --seed s1

# 确认后加 --yes 才真正生成（会花钱）
node scripts/quality-eval/summary-regenerate.mjs … --yes
```

- 生成模型来自 CLI 配置的 `[llm]`（`--config`，不写用 CLI 默认配置）。抽样用和评审相同的函数，**同一个 `--seed`、`--daily`、`--notes` 抽到同一批论文**。
- 日报条目走日报流水线自己的带校验重试的函数：模型的回答不合格时最多尝试 3 次，仍不合格就按流水线的做法记为回退（原因写在记录里）。详细笔记走流水线的详细笔记函数，只请求一次。所以计划里的“最多请求数”是日报条目数 × 3 加上笔记数。模型端点连不上不记为结果，而是记为出错，下次运行重试；连续 3 次出错就停止。
- 详细笔记提示词里的主题名取 CLI 配置里该主题 tag 对应的名称，没有就用 tag；记录里写明用了哪个。
- 结果放在 `--out/summaries/<类型>-<编号>.json`：生成模型和推理设置（不含接口地址与密钥）、生成提示词的哈希、原文版本与内容哈希、输出（日报是五个字段或回退原因，笔记是 Markdown）、请求次数、用量、耗时。`run.json` 记录参数、种子和抽样。
- 可以中断后继续：生成模型、提示词哈希和原文内容哈希都没变的条目会跳过；`--regenerate` 全部重做。

## 评审重新生成的摘要

基线评审评的是**重新生成**的摘要（见上一节）：先 `summary-regenerate.mjs`，再把它的 `--out` 目录交给评审：

```sh
node scripts/quality-eval/summary-judge.mjs --judge-config ~/judge.toml --sources ~/quality-eval/summary-sources \
  --summaries ~/quality-eval/regen-1 --out ~/quality-eval/judge-regen-1          # 先看计划
node scripts/quality-eval/summary-judge.mjs … --yes                               # 真正评审
```

- `--summaries` 时被评的论文就是重新生成那次 `run.json` 里记录的抽样，所以不要再给 `--daily`、`--notes`、`--ids`、`--from`、`--to`、`--include-older-notes`，也不需要 `--vault`。生成模型取自那次的记录，不会去读 CLI 配置（除非你显式给 `--config`）。评审模型仍必须与它不同。
- 日报条目评的是模型返回的五个字段原值，笔记评的是重新生成的 Markdown 按 `##` 拆开的各章节。回退（写明原因）、出错、缓存原文已变化（内容哈希对不上）、没生成的条目会单列跳过，不替换。
- 报告“评审对象”里有“被评摘要来源”：重新生成（生成模型、推理设置、生成提示词哈希、生成时间、输出目录）。重新生成的摘要被改写后再评，会重新评审（续跑判断加入了被评摘要的内容哈希）。
- 不带 `--summaries` 评 Vault 里的历史摘要时，报告写明来源是“历史 Vault”，并把缓存原文版本高于 v1 的条目标出来（“原文已有新版本（vN），生成时可能看到的是旧版”），评审对象里给出条数，判定分布另给一张只含 v1 原文条目的表。这类评审只作参考。
- `--offline` 对照的是 Vault 里的历史文字，与重新生成的摘要无法对照；和 `--summaries` 一起给时会跳过，报告里说明原因。

## 让第二个模型复核评审提出的问题

评审模型也会看错。与其让研究者逐条核对所有评审问题，不如让另一个模型先把评审提出的**每一个**问题复核一遍，研究者只裁定两边有分歧的。

```sh
# 先看计划：有多少条目有评审问题、最多多少次请求、输入规模。不调用模型，不写文件。
node scripts/quality-eval/summary-meta-review.mjs --judged ~/quality-eval/judge-1 --sources ~/quality-eval/summary-sources \
  --config ~/.config/arxiv-daily/config.toml --reviewer-model <复核模型名> --reviewer-effort xhigh --out ~/quality-eval/meta-1

# 确认后加 --yes 才真正调用（会花钱）
node scripts/quality-eval/summary-meta-review.mjs … --yes

# 之后只想重新生成报告（不调用模型）
node scripts/quality-eval/summary-meta-review.mjs --report-only --out ~/quality-eval/meta-1
```

- 复核模型用 CLI 配置 `[llm]` 里的接口和密钥，`--reviewer-model` 和 `--reviewer-effort` 覆盖模型名和推理强度（强度原样传给接口，`xhigh` 之类也行；不同服务商支持不同，用 `anthropic` 服务商时 `xhigh` 会被降成 `high`）。复核模型必须与评审模型不同，可以与生成模型相同。
- 每个有评审问题的条目发一次请求，没有问题的条目不发。复核模型看到的原文和被评摘要与评审完全相同，再加上按编号列出的评审问题，逐条回答：同意 / 不同意 / 拿不准、评审的严重程度合不合适（合适 / 偏重 / 偏轻）、中文理由，可附原文引用。回答不合格（编号缺漏、理由不是中文、引用不在原文里等）会纠正重试一次，仍不合格记为无效。
- 评审的是 Vault 里的历史摘要时要给 `--vault`，用来还原评审当时看到的内容；评审后摘要或原文变过的条目会跳过并写明原因。
- 可以中断后继续：复核模型、推理强度、复核提示词和评审结果都没变的条目会跳过，`--rereview` 全部重做。
- 输出：`meta/`（每条一个文件）、`run.json`、`meta-review.md`（复核一致率、按维度/严重程度/类型的分布、严重程度意见、不同意和拿不准的清单）、`meta-review.json`。

### 只把分歧交给研究者

```sh
node scripts/quality-eval/summary-review.mjs --meta ~/quality-eval/meta-1 --sources ~/quality-eval/summary-sources \
  [--agreed-sample 3] [--count N] [--seed 种子] --out ~/quality-eval/review-meta-1
# 在浏览器里打开 review.html，裁定完点“导出结果”，然后：
node scripts/quality-eval/summary-review.mjs --import 导出的结果.json --out ~/quality-eval/review-meta-1
```

- 页面里的卡片是复核模型不同意或拿不准的所有评审问题（默认不限数量，`--count` 给了就限制整页的条数，分歧优先），再加几条双方都同意的问题作抽查（`--agreed-sample`，默认 3，0 为不抽），抽查的卡片明确标着“复核同意的抽查”。
- 卡片上同时显示评审的说明和复核的裁定、严重程度意见与理由（有引用时附原文上下文）。分歧卡片的按钮是“评审对 / 复核对 / 拿不准”；抽查卡片是“同意 / 不同意 / 拿不准”（同意 = 评审和复核都对）。
- 导入后的 `calibration.md` / `calibration.json` 合并了复核的结果：复核一致率；分歧条目里研究者站评审、站复核、拿不准和未回答的条数（总体、按维度、按严重程度）；抽查的同意率；以及**评审精确率的估计** =（复核同意的问题数 × 抽查同意率 + 研究者站评审一边的分歧数）/ 全部问题数。它只是估计（抽查样本很小，复核模型也会错），报告里同时给出各个组成部分；拿不准和未回答的分歧在点估计里按“评审错”算，上界里按“评审对”算。最后列出研究者不认同评审的条目和备注。
