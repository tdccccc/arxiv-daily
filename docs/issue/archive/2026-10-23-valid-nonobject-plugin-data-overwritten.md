# 合法 JSON 但不是对象的插件设置仍被静默覆盖

状态：已修复（分支 `fix/2026-10-23-followups`，提交 7738623）

> 来源：2026-10-21 修复交接中的额外发现，2026-10-23 复核；不计入原 54 条。
> 严重程度：中 · 置信度：代码路径已核对

## 问题与依据

`readPersistedData()` 对 `loadData()` 返回的 `[]`、`42`、字符串或 `null` 直接接受；`plugin/src/settings/load.ts` 的 `settingsAndStateFromPersistedData()` 将非普通对象替换为 `{}`，没有格式警告。插件按默认值启动，后续保存可以覆盖原文件。第二批 OBS-08 保护的是 JSON 解析失败，未覆盖合法但结构错误的文件。

## 建议和验收

区分文件不存在与文件存在但顶层无效；对后者沿用备份和提示流程。测试数组、数字、字符串、null，验证原文保留、用户收到提示；首次启动无文件仍正常。

## 修复情况

data.json 是合法 JSON 但顶层不是对象（`[]`、数字、字符串、布尔值或字面量 `null`）时，插件不再悄悄按默认设置启动并在下次保存时覆盖它：现在会像对待无法解析的文件一样，把原文件复制成 `data.json.corrupt-<修改时间>`，用默认设置启动，并弹出提示和写启动日志，原文件保持原样。因为 Obsidian 的 `loadData()` 对“文件不存在”和字面量 `null` 都返回 `null`，插件现在在拿到非对象结果时再通过文件夹接口确认文件是否真的存在；不存在才算正常的首次启动。代价是首次启动多一次文件存在检查；文件修好之前插件跑在默认设置上，需要从副本里找回设置。测试：`corrupt-data-json.test.ts` 新增 9 条（数组、数字、字符串、布尔值、字面量 null 各自留下副本并提示、重复启动只留一份、副本写不出时拒绝启动、Obsidian 第一次读失败后重读成功、无文件仍是首次启动），并更新了原“无文件”用例的断言。
