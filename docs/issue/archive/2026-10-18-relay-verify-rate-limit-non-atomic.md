# 邮件中继验证码限流是非原子的 KV 读改写，并发请求可绕过按邮箱和按 IP 的上限

> 发现日期：2026-10-18 · 来源：main `21fe2ce` 深度代码审查 · 编号 CLI-9
> 范围：`services/email-relay` `/v1/verify/start` · 严重程度：低 · 状态：已修复（待部署）（分支 `fix/followup-relay-ratelimit`；先前的部分修复见 `fix/2026-10-18-review` 提交 84046ae） · 置信度：代码推断

## 问题

`/v1/verify/start` 无需认证，会从项目的 Resend 域名向任意地址发邮件。上限（每地址每小时 3 次、每 IP 每小时 10 次）通过 Workers KV 的"读—比较—写"实现。KV 最终一致（读可能落后约 60 秒），没有比较并交换，N 个并发请求都读到 0 并全部通过，攻击者可以对受害者地址邮件轰炸、消耗 Resend 发送信誉和额度，远超宣称的上限。

另外地址计数先于 IP 计数递增：已被 IP 限流的攻击者仍会消耗受害者地址每小时的 3 个名额，让真正的地址主人收不到验证邮件。

`kv.ts` 已注明这些限制是尽力而为，属于已知局限，不是回归。

## 原因

- `services/email-relay/src/kv.ts:222` `checkAndIncrRateLimit` 先读再写（带 `expirationTtl`），无原子计数。
- `services/email-relay/src/index.ts:106-127` `verifyStart` 先检查邮箱再检查 IP。

## 可能的解决方案

推荐（分两步）：
1. 本次：先检查 IP 上限，再检查邮箱上限，避免已被 IP 限流的请求消耗受害者地址的名额。
2. 后续：把计数器移入 Durable Object（已有 DeliverGate 命名空间），按 hash(email) / hash(IP) 事务性递增；或在路由前加 Cloudflare 速率限制规则。这涉及部署与 Cloudflare 配置变更，需单独评估。

## 修复后应补的测试

- IP 已超限时请求被拒绝，且邮箱计数不增加。

## 修复情况

已改为先检查 IP 上限再检查邮箱上限，被 IP 限流的请求不再消耗受害者地址的名额（新测试在旧顺序下失败）。

**余项已修复（代码完成，待用户部署）**：验证码限流计数器不再用 KV 读改写，改为放进 Durable Object（新类 `VerifyRateLimiter`，绑定 `VERIFY_RATE_LIMIT`）。每个 IP、每个邮箱各对应一个独立的计数对象，对象名是用 TOKEN_SECRET 做密钥哈希后的值，不保存原始邮箱或 IP。"检查并加一"在对象内一次同步完成，同一时刻的并发请求不会再一起读到旧值，所以每个地址每小时最多发 3 封、每个 IP 每小时最多发 10 封，和之前对外宣称的上限一致。窗口从该对象的第一次请求算起满一小时后重新计数；对象里始终只有一行记录，窗口结束时由定时闹钟清空，不会无限累积存储。仍然先检查 IP 再检查邮箱，被 IP 限流的请求不消耗邮箱名额；被限流时返回的状态码和内容与以前完全一致（对外仍是"已发送"的 200 响应）。旧的 KV 限流代码已删除，旧的 `rl:` 键会按 TTL 自行过期。如果部署时没绑定这个 Durable Object，该接口会直接报错且不发信（宁可拒绝也不放开限制）。

**只有用户部署后才生效**：需要在 `services/email-relay` 下运行 `npm run deploy`（即 `wrangler deploy`），它会自动应用新增的迁移 `v2-verify-rate-limiter`。部署后第一个小时内，每个地址和 IP 的计数从零开始，可能多放行一个窗口的额度。新增测试覆盖：并发 25 个请求同一地址恰好放行 3 个、同一 IP 并发 30 个恰好放行 10 个、IP 限流不增加邮箱计数、一小时后窗口重置、计数对象名为哈希而非原始值。
