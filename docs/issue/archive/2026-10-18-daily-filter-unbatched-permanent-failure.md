# 日报过滤把当天所有候选塞进一个 LLM 请求；上下文超长被当成永久失败，那一天再也不会重试

> 发现日期：2026-10-18 · 来源：main `21fe2ce` 深度代码审查 · 编号 CORE-06
> 范围：日报流水线论文过滤 · 严重程度：中 · 状态：已修复（分支 `fix/2026-10-18-review`，提交 c14e5df） · 置信度：代码推断

## 问题

`buildPaperFilterRequest` 把当天所有候选（所有已选分类，含交叉列表）的编号、标题、完整摘要拼成一条用户消息，不分批、不截断摘要、不设上限，并要求一次回复给出每篇的 JSON 记录。cs.LG / cs.CV / cs.CL 这类大分类或多分类组合很容易超过 20 万 token。

- 服务端对超长提示返回 HTTP 400（context_length_exceeded）。`isPermanentLlmError` 把除 429 外的所有 4xx 都当永久错误，流水线返回 `failed_permanent`，调度器认为这一天已完成，不再自动重试。订阅分类多的用户可能每天都失败。
- 408 / 409 / 425（网关超时、冲突）也被归为永久错误。
- 回复被输出上限截断时 JSON 无效；温度 0 下同一请求每轮都同样失败，直到 10 次上限变成永久失败，白白花掉十次整日调用。
- 检查点是全有或全无，一次模型抖动丢掉一整天的过滤。

## 原因

- `packages/core/src/pipeline/paper-filter-contract.ts:153-160`：拼接全部论文。
- `packages/core/src/pipeline/paper-filter.ts:223`：只调用一次 `llm.call`。
- `packages/core/src/llm/client.ts:467-475`：`isPermanentLlmError` = 除 429 外的任意 4xx。
- `packages/core/src/pipeline/pipeline.ts:279-282` 与 `state-store.ts:137-162` 使其成为终态。

## 可能的解决方案

推荐：
1. 按字符/估算 token 预算分批（预算设得足够大，普通日子仍是一次调用，只有超大日子才拆分），每批单独检查点（检查点本来就按请求内容哈希），合并结果，"省略即跳过"的约定按批生效。
2. 收窄 `isPermanentLlmError`：408 / 409 / 425 视为暂时错误；401 / 403 / 404 保持永久。
3. 备选：提示过长时在发送前给出明确可操作的错误，而不是把这一天永久标记失败。

## 修复后应补的测试

- 超过预算的候选集被拆成多批，结果合并正确，每批有独立检查点。
- 普通规模候选集仍是一次请求（与现有检查点兼容）。
- 408/409/425 被判为暂时错误。

## 修复情况

按 40 万字符预算分批：普通日子仍是一次请求、检查点格式不变；超大日子按顺序分批，每批一个检查点（`<date>.batch-<n>.json`），结果合并。HTTP 408 / 409 / 425 改为暂时错误。上下文超长的 400 仍判为永久错误，靠分批避免触发。
