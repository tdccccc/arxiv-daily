## Intent

让"日报里每篇论文的摘要"和"详细笔记"写得好不好可以被反复、可比地测量：一套不调用模型的自动检查给出格式、回退和数字可溯源等硬指标；一个大模型评审对照模型当时看到的原文，逐篇判断有没有说错、有没有漏掉关键结果。改提示词或换模型前后，用同一批论文跑一遍就能直接对比。

## Success criteria

- [x] 一条开发者命令扫描一个 Vault 里已生成的日报和详细笔记（可按日期范围），不调用模型，输出一份可留存的报告，至少包含：回退率及原因、公式格式违规、字段长度（仅作参考数据，不算问题）、"原文未说明"占比、摘要中数字在原文里找不到的条目清单；固定测试覆盖每项检查。
- [ ] 一条开发者命令对抽样的日报条目和详细笔记运行大模型评审：拿到与生成时同口径的原文输入，按固定评分维度逐条判断准确（有没有原文不支持或说错的内容、是否混淆作者声称与已证实结果）、完整（有没有漏掉最重要的结果、关键条件或限制）、清楚（读者能否不看原文就理解每个字段说的是什么）逐篇给出判定和依据，汇总成可留存的报告；运行前先显示请求数和估算规模，加确认参数才真正调用；评审模型单独配置（接口、模型名、密钥），必须与生成模型不同。
- [ ] 评审的可信度有一次核对：研究者对不少于 10 条评审判定给出"同意 / 不同意"，报告记录一致率。
- [ ] 至少一次真实基线：自动检查跑过真实 Vault 全部历史，大模型评审跑过一批抽样（运行前征得用户同意费用），两份报告留存在仓库外的评估目录。

## Non-goals

- 产品界面里的质量反馈按钮，或进入 CLI / 插件的用户命令。
- 用评估结果自动改提示词或自动重写摘要。
- 让用户自定义提示词（2026-10-28 已决定暂不做）。
- 作为 CI 或发版门槛；普通测试和 CI 不调用模型 API、不访问网络。
- 筛选标注的扩充：由研究者用现有 `scripts/quality-eval` 工具另行进行（筛选记录需要再积累两三周的日报），不在本计划内。

## Constraints

- 工具放在 `scripts/` 下，与 `scripts/quality-eval` 同类，作为开发者工具；复用 core 里现有的报告解析、格式校验、原文获取和模型调用代码，不复制一套平行实现。
- 评审输入必须与生成时同口径（同样的摘要 / 正文片段预算）；拿不到同口径输入的条目在报告中单列，不混入评分。
- 真实模型运行会产生费用，每次运行前先征得用户同意。
- 不把 API 密钥或接口地址写进报告、日志或仓库。
- main 只接受 PR：在功能分支上开发，推送和开 PR 需用户逐次同意。
- 实现块默认交给 subagent（Sonnet，最多 3 个并行，不再派生，结论写进 .txt/.json 文件）；owner 验收。
- 评审模型必须与生成模型不同（用户 2026-10-28 决定）；接口与密钥由用户提供，单独的配置文件，不改用户的 CLI 配置。
- 分支 `feat/summary-quality-eval`。
- Commits: checkpoint commits authorized（用户 2026-10-28 授权：每个验收通过的块单独提交，阶段切换时提交 Helm 文件）。不推送，推送与 PR 需用户逐次同意。
